# AI Sana Tasks

MVP платформы для подготовки, рейтинга и открытого выбора бизнес-задач. Представитель бизнеса превращает слабое описание в подтверждённую карточку, повышает её рейтинг полноты и публикует в каталоге. Студенческие команды самостоятельно выбирают задачи и отправляют предложения, а бизнес вручную принимает или отклоняет их.

> Организационный риск: в кейсе указана команда из 3–5 участников. Нас двое, поэтому до старта нужно подтвердить у организаторов допустимость такого состава или найти третьего участника.

## Статус

Backend реализует полный сценарий MVP: анализ описания, создание и редактирование карточки, подтверждения и рейтинг, публикация, каталог, профили команд, отклики и ручные решения бизнеса.

- Данные сохраняются в локальном JSON; при первом запросе автоматически создаются 5 задач с исходными описаниями, 5 команд и 5 откликов.
- Без ключа работает явно обозначенный `mock`; адаптер OpenAI подключается через `.env.local`.
- Frontend Task Hub подключён к API: главная, каталог, мастер создания, редактирование, публикация, отклики и ручной выбор команд. Логотипы находятся в `public`.
- По умолчанию `NEXT_PUBLIC_DATA_MODE=api`: данные сохраняются на сервере. `AI_PROVIDER=mock` отдельно управляет только AI, предупреждения показываются в интерфейсе.
- Настройки и проверка фронта: **[docs/frontend-integration.md](docs/frontend-integration.md)**.
- Подробные контракты, примеры `fetch` и порядок интеграции: **[docs/API.md](docs/API.md)**.

- frontend работает в `src/app` и `src/components`;

## Обязательный пользовательский сценарий

1. Бизнес вводит слабое описание потребности или проблемы.
2. Система определяет недостающие сведения и задаёт минимум три уместных вопроса.
3. Из описания и ответов формируется редактируемая карточка.
4. Бизнес вручную подтверждает поля.
5. Сервер рассчитывает рейтинг от 0 до 100 и объясняет начисление.
6. Задача публикуется в общем каталоге независимо от рейтинга.
7. Студенческая команда отправляет идею, план, срок и ссылку.
8. Бизнес вручную принимает или отклоняет предложение.

AI не публикует задачу, не добавляет неизвестные пользователю факты и не выбирает команду.

## Поля карточки

- название;
- исходное описание;
- отрасль и тема;
- контекст и потребность;
- доступные данные и материалы;
- ожидаемый результат;
- критерии успеха;
- ограничения;
- целевые пользователи;
- контакт бизнеса;
- формат взаимодействия.

Актуальная машинно-проверяемая схема находится в `src/shared/contracts.ts`.

## Рейтинг готовности

| Показатель             |   Баллы |
| ---------------------- | ------: |
| Контекст и потребность |      20 |
| Данные и материалы     |      20 |
| Ожидаемый результат    |      15 |
| Критерии успеха        |      15 |
| Ограничения            |      10 |
| Пользователи           |      10 |
| Связь с бизнесом       |      10 |
| **Всего**              | **100** |

Баллы начисляются сервером только за заполненные и подтверждённые человеком поля. AI не рассчитывает итоговый рейтинг. Каждый показатель начисляется целиком или даёт 0; для «Связи с бизнесом» нужны одновременно подтверждённые `businessContact` и `interactionFormat` (формат встреч и обратной связи).

При изменении значения подтверждение этого поля снимается, если запрос явно не содержит новый список `confirmedFields`. Смена исходного описания без нового списка снимает все подтверждения. Пустое поле подтвердить нельзя. API возвращает `scoreBreakdown`, `missingFields`, `unconfirmedFields`. Рейтинг отражает полноту и подтверждение сведений, а не их объективную достоверность.

Уровни готовности:

- 0–39 — черновик;
- 40–69 — рабочая;
- 70–89 — готовая;
- 90–100 — приоритетная.

Низкий рейтинг не скрывает задачу и не запрещает отклик. Рейтинг влияет на позицию в каталоге и пересчитывается после подтверждённых изменений.

## Рабочий API

| Метод          | Маршрут                     | Назначение                                            |
| -------------- | --------------------------- | ----------------------------------------------------- |
| `GET`          | `/api/health`               | Проверка приложения, хранилища и количества записей   |
| `POST`         | `/api/ai/questions`         | Анализ черновика и минимум 3 вопроса                  |
| `POST`         | `/api/ai/card`              | Формирование несохранённой, неподтверждённой карточки |
| `GET`          | `/api/tasks`                | Опубликованный каталог, сортировка и фильтры          |
| `POST`         | `/api/tasks`                | Создание черновика                                    |
| `GET`, `PATCH` | `/api/tasks/:id`            | Чтение, редактирование и подтверждение полей          |
| `POST`         | `/api/tasks/:id/publish`    | Публикация после ручного подтверждения                |
| `POST`         | `/api/tasks/:id/archive`    | Архивирование без удаления истории                    |
| `GET`, `POST`  | `/api/teams`                | Список и создание профилей команд                     |
| `GET`          | `/api/teams/:id`            | Профиль команды                                       |
| `GET`, `POST`  | `/api/tasks/:id/proposals`  | Отклики на задачу                                     |
| `GET`          | `/api/proposals`            | Отклики с фильтром по команде и статусу               |
| `PATCH`        | `/api/proposals/:id/status` | Ручное принятие или отклонение                        |

`GET /api/tasks` возвращает `{ tasks, total }`, по умолчанию только опубликованные задачи. Кабинет бизнеса использует `?status=all` или `?status=draft`. Фильтры: `topic`, `industry`, `readinessLevel`, `q`. Сортировка: рейтинг по убыванию, затем новые задачи. Детали и мутации возвращают `{ task }`, `{ team }` или `{ proposal }`; AI имеет отдельный формат — [см. примеры](docs/API.md).

Формат ошибки API:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Human-readable description",
    "details": []
  }
}
```

## AI-контракт

Первая функция анализирует черновик и возвращает:

- минимум три уточняющих вопроса;
- поле карточки, к которому относится вопрос;
- причину вопроса;
- список недостающих полей.

Вторая функция получает исходный текст, введённые поля и ответы `{ field, answer }`. Возвращает `{ card, confirmedFields: [], ai }`; сама не сохраняет карточку. Результат нужно передать в `POST /api/tasks`, затем дать человеку отредактировать и подтвердить поля.

OpenAI использует Responses API и Structured Outputs по [официальной документации](https://developers.openai.com/api/docs/guides/structured-outputs). Промпты находятся в `src/server/ai/prompts.ts`. Кроме проверки Zod, непустые значения карточки сверяются с текстом пользователя: разрешены только фрагменты исходного текста. Изменения регистра, пробелов и завершающей пунктуации восстанавливаются до исходной цитаты. Неподтверждённые текстом предложения отдельных полей отбрасываются с предупреждением в `ai.warning`, остальные поля сохраняются. Если модель пропустила контекст, сервер использует исходное описание; явно очищенное пользователем поле остаётся пустым. Пользовательские правки и ответы имеют приоритет. Эта проверка ограничивает свободный пересказ; корректность смысла извлечённых фрагментов всё равно подтверждает человек.

`ai.provider`, `ai.fallback` и `ai.warning` позволяют интерфейсу честно показать деморежим, сбой провайдера или отброшенные предложения. В `mock` внешних запросов нет; вопросы формируются из шаблонов и незаполненных полей. При таймауте, отказе или повреждённой структуре ответа OpenAI включается помеченный fallback, если `AI_FALLBACK_TO_MOCK=true`. При `false` возвращается 502. Сервер пишет только безопасную категорию ошибки и HTTP-статус провайдера, без ключей, текста запросов и сообщений провайдера. Реальный вызов требует собственного ключа и модели с поддержкой Structured Outputs; автоматические тесты не обращаются к платному API.

## Хранилище и ограничения MVP

`DATA_FILE_PATH=./data/db.json` разрешается относительно корня проекта. Первый запрос к API данных или health создаёт демонстрационную базу. Существующий файл не пересоздаётся. Записи выполняются через временный файл и атомарное переименование; lock-файл защищает от конкурентных записей. Повреждённая база возвращает `503 STORAGE_INVALID`, а не затирается тестовыми данными.

Для новой демобазы укажите другой `DATA_FILE_PATH` и перезапустите сервер. После аварийного завершения процесса может остаться `<DATA_FILE_PATH>.lock`: остановите все процессы приложения, сохраните копию базы и только затем удалите именно этот lock-файл. При обычном завершении запросов он удаляется автоматически.

JSON рассчитан на локальный хакатонный сервер с постоянным диском. Для serverless, нескольких машин и production потребуется другое хранилище. Авторизации нет: роли демонстрационные, все API доступны пользователю приложения. Не публикуйте такой экземпляр с реальными приватными данными или платным AI-ключом в открытый интернет без контроля доступа.

## Проверка backend

```powershell
pnpm check
pnpm test:smoke
```

Unit-тесты проверяют рейтинг и его границы, снятие подтверждений, состояния задач, фильтры, решения по откликам, JSON-транзакции, входные ошибки и AI-fallback. Smoke-тест сам запускает production-сервер на свободном локальном порту с отдельной временной базой и `AI_PROVIDER=mock`, проходит HTTP-сценарий и перезапускает сервер для проверки сохранения данных. Рабочая база не затрагивается.

## Git-процесс для двух человек

1. Не работать напрямую в одном длинном branch.
2. Использовать короткие ветки `backend/<задача>` и `frontend/<задача>`.
3. Перед началом новой задачи обновляться от `main`.
4. Делать небольшие коммиты в формате Conventional Commits:
   - `feat: add task draft endpoint`;
   - `fix: recalculate readiness after confirmation`;
   - `docs: update demo flow`.
5. Не коммитить `.env.local`, ключи и содержимое `data/*.json`.
6. Перед merge запускать `pnpm check`.
7. Интегрировать изменения регулярно, не оставлять объединение на последние 30 минут.

## Не входит в MVP

- полноценная регистрация и восстановление пароля;
- сложная ролевая модель;
- чат, уведомления и календарь;
- файловое хранилище;
- собственная ML-модель и векторная база;
- автоматическое назначение команды;
- production-инфраструктура;
- полноценный проектный трекер.

Для демонстрации роли можно переключать явным контролом «Бизнес / Команда» без авторизации.

## Обязательная демонстрация

За пять минут нужно в работающем приложении:

1. ввести слабое описание;
2. ответить на AI-вопросы;
3. показать заполненную карточку и рост рейтинга;
4. опубликовать задачу;
5. открыть её от лица команды;
6. отправить предложение;
7. вернуться к роли бизнеса;
8. принять или отклонить предложение.

Все переходы должны работать в MVP, а не на слайдах.
